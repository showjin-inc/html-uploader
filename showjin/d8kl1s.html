権限境界からつくるチャット

社外ゲストを含む B2B チャット + ナレッジ基盤です。技術選定のほとんどは「誰に何を見せないか」から逆算されています。 この文書は、その逆算の道筋をエンジニア向けに説明します。

2026-09-24 Sprint 2 進行中 TypeScript / Node 24 / AWS ap-northeast-1

What it isこれは何か

社内メンバーと社外ゲストが同じ画面で会話し、その会話からナレッジを育てる製品です。Slack や Teams との違いは、ゲストに過去を見せないという要件を機能ではなく設計の中心に置いている点です。

  • Room — 通常 Room / Secret Room / ゲスト Room / ゲスト DM の4種。それぞれ参加者の範囲と履歴の見え方が違います。
  • ゲスト — 他社の人を特定の Room にだけ招く。from_join なら参加した瞬間より前の発言は 存在ごと見えません。
  • ナレッジ化 — 会話から候補を抽出し、承認を経て正式ナレッジにする（M7 以降）。
  • AI — 会話の文脈を使った回答。ただし AI が読める範囲は、それを起動した人が読める範囲と完全に一致します。

The constraintいちばん重要な制約

設計書で凍結されている要件のうち、実装コストを最も左右しているのは次の3つです。ここを理解すると、後続の技術選定がすべて説明できます。

1. 403 ではなく 404 を返す

権限のないリソースは「アクセス拒否」ではなく「存在しない」と答えます。403 は そこに何かがあることを教えてしまうためです。Secret Room の ID を総当たりされても、存在する Room と 存在しない Room の応答が1バイトも違わないことをテストで保証しています。

2. Full Admin は管理者であって閲覧者ではない

会社の最高管理者であっても、自分が参加していない Room の中身は読めません。一覧にも出ません。 「管理権限があれば全部見える」という一般的な前提を、この製品は採用していません。

3. 履歴境界は visibility_from_seq ひとつ

「この人はこの Room の何番目の発言から見てよいか」を1つの数値で表し、HTTP・検索・AI・リアルタイム配信のすべてが同じ数値を参照します。境界の実装が4つあれば、いつか3つが正しくて1つが間違います。

3つ目が特に効いています。たとえばリアルタイム配信で「メッセージが編集された」という通知を送るとき、本文を含まない メタデータだけの通知であっても、参加前の発言についてはゲストに届けてはいけません。「そこに何かがある」と伝わってしまうからです。

  • ブラウザ → API HTTPS。OpenAPI で型もバリデーションも固定
  • ブラウザ → API → Redis WebSocket 接続用チケットの発行。60秒・1回きり

要点は Worker から Aurora への線が2本あることです。1本目は「何が起きたか」を読む線、2本目は「いま誰に見せて よいか」を配信の直前に問い直す線です。Redis は誰が接続中かを知っていますが、誰に見せてよいかは知りません。後者を省くとこの製品は成立しません。

Why these toolsなぜこの構成なのか

一般的な選択肢ではなく、こちらを選んだ理由を書きます。太字が「この製品固有の理由」です。

契約とバリデーション

採用 なぜ必要か
OpenAPI 3.1
（凍結・SHA-256 検証）		 API 仕様を SHA-256 で固定し、CI が毎回ハッシュを照合します。仕様の書き換えは実装上の問題の解決策にならないという運用ルールを、レビューではなく機械で担保するためです。
express-openapi-validator
（リクエスト＋レスポンス両方向）		 リクエストだけでなくレスポンスも実行時に検証します。契約外のフィールドをサーバーが 返してしまう事故＝そのまま情報漏洩だからです。実測コストは p95 で +0.070ms でした。
openapi-typescript
+ openapi-fetch		 フロントの型を仕様から生成。生成物のドリフトを CI が検出するので、画面側が手書きの URL やレスポンス型を持てません。

データ

採用 なぜ必要か
Aurora PostgreSQL トランザクション・行ロック・部分ユニークインデックスが要件に直結します。特に seq 採番 （Room 内の連番）は行ロックとユニーク制約の組み合わせで、欠番も重複も起こさないことを保証しています。
Kysely + pg
（ORM を使わない）		 型は付けたいが SQL は隠したくない。権限判定のクエリは読めることが重要で、ORM が生成する SQL を推測しながらレビューしたくないためです。
SQL 直書きマイグレーション CHECK 制約・部分ユニークインデックス・トリガを「DB 側の契約」として明示するため。マイグレーションツールの 抽象化に載せると、これらが表現できないか、表現できても読めなくなります。
Transactional Outbox イベント行を業務データと同じトランザクションで書きます。別々に書くと「保存されたが配信されない」 「配信されたが保存されていない」が発生します。配信は at-least-once なので、ハンドラは冪等に書きます。

認証・リアルタイム

採用 なぜ必要か
Cognito
+ aws-jwt-verify		 パスワード管理・リセット・MFA を自前で持たないため。ただしJWT の署名が正しいことは「今この人が操作してよい」を意味しません。アカウント状態・所属状態・セッション・端末をリクエストごとに DB で再評価しています。
接続チケット
POST /realtime/tickets		 ブラウザは WebSocket に Authorization ヘッダを付けられません。URL に JWT を載せる実装が世の中にありますが、 URL はログ・プロキシ・履歴・Referer に残ります。代わりに32バイトの不透明な乱数を発行し、 サーバーは SHA-256 だけを保持、TTL 60秒・1回使ったら消滅、とします。
Redis（ElastiCache） 「誰がどの Room に接続中か」の一時台帳。Redis は権限の根拠ではありません。 全損しても「配信されなくなる」だけで、「見えてはいけないものが配信される」は起きない設計です。
API Gateway WebSocket
検証待ち		 初期候補。1通を N 人に配ると N 通分の課金になるため、宛先数が増えると専用ゲートウェイが安くなります。 分岐点は月4,760万配信と試算済みで、これを AWS 上で実測してから確定します。

実行環境

採用 なぜ必要か
ECS Fargate API と Worker を同じ TypeScript スタックで動かします。EC2 の OS 管理を持たないため。
Worker を分離 Outbox 配信・保持期間の失効処理・通知をリクエストの外に出すため。配信のファンアウトを POST /messages のレイテンシに入れないのが目的です。
OpenSearch M4 から 日本語全文検索。kuromoji と n-gram の品質比較を M4 前に行う予定。検索結果にも同じ権限境界を適用する必要があるため、インデックスの設計が権限設計に従属します。
S3 + GuardDuty M5 から 添付ファイル。スキャン完了までは pending 状態で、他の参加者にも見せません。

Request pathリクエストが通る道

すべての API リクエストがこの順で処理されます。順番自体が仕様で固定されています。

  1. Request ID 付与 HTTP → Outbox → Worker → リアルタイムまで1つの ID で追跡する
  2. 認証（JWT 検証） 署名・発行元・有効期限。アクセストークン以外は受け付けない
  3. 実効状態の再評価 アカウント凍結・所属停止・セッション失効・端末失効を DB で確認。トークンが有効でもここで止まる
  4. 権限判定 リソースごとに Permission Service へ問い合わせ。この前に本文を読まないのが規約
  5. リクエスト検証 OpenAPI に対する実行時検証。未知のフィールドは 422 で拒否
  6. ドメイン処理 トランザクション内で業務データを書く
  7. Outbox 書き込み 同一トランザクション。ロールバックすればイベントも消える
  8. 監査ログ メタデータのみ。本文・引用・ファイル内容・AI 回答は書き込み前に機械的に拒否される
  9. レスポンス検証 → エラー変換 契約外の応答は 500 に変換し、問題のある本文は送信しない

認証がバリデーションより前にあるのは意図的です。バリデータ自身の認証機能は Bearer nonsense を通してしまうことが事前検証で分かっており、認証として使えないためです。

テストの方針

セキュリティ要件は「実装した」ではなく「壊すとテストが落ちる」状態にしています。たとえば履歴境界の判定を 1行消すと、HTTP のテストとリアルタイム配信のテストの両方が落ちます。実装したあと 実際に消して確認しています。

For reviewersコードを見る人へ

レビューで見てほしい不変条件です。ここが崩れていたら指摘してください。

  • 404, not 403. 権限のないリソースは RESOURCE_NOT_FOUND。理由はログにだけ書く
  • 権限主体は DB 由来。 PermissionSubject は private symbol を持つので、リクエスト入力から組み立てられない
  • 権限判定が本文取得より前。 ハンドラの最初の仕事が認可
  • 境界はどこでも同じ。 HTTP / 検索 / AI / リアルタイム、メタデータのみの通知も含む
  • Outbox は同一トランザクション。 ハンドラは冪等
  • 監査はメタデータのみ。 本文を含むキーは挿入前に例外
  • ログに秘密と本文を入れない。 シリアライズ時に落とす仕組みはあるが、頼らない
  • 配信先は配信時に再判定。 Redis の集合は候補であって権限ではない

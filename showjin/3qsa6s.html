Showcase v2

\n

AI-Native Operations OS — 仕様概要 / Engineering & AI Build Brief

\n
  • Version: 0.2
  • Date: 2026-09-01
  • Status: Showcase v2 / Test Edition
  • 対象: 株式会社コパン社内業務システム Showcase
  • 想定読者: 社内エンジニア、AI開発エージェント、業務設計担当者
  • 目的: 現行Showcaseを壊さず、別系統のv2テスト環境で「AIが業務を観測・判断・実行支援・評価・改善する」次世代業務OSを実証する

0. この資料の結論

\n

Showcase v2は「ShowcaseにAIチャットを付ける計画」ではない。

目指すものは、

コパンで発生する業務イベントを常時観測し、AIが状況を理解し、次の行動を判断し、許可された範囲では実行し、その結果と人間の修正から継続的に改善する AI-Native Operations OS

である。

v2で検証したい本質は以下の5点。

  1. 人が探して考える前に、Showcaseが「今やるべき仕事」を出せるか
  2. 入力・報告・転記・検索・要約・追客・監視などの非付加価値業務を大幅に消せるか
  3. 企業・スタッフ・案件・営業・面談・稼働のデータを一つの判断系としてAIが扱えるか
  4. AIの判断をTrace / Eval / Human Correctionで測定し、短いサイクルで改善できるか
  5. コパンで作った仕組みを、将来ほかの花業界業務にも展開可能なAI業務基盤にできるか

Showcase v2はテスト版であるが、機能構想自体をフェーズで制限しない。

最前線の技術を使い、コパンの業務をどこまでAIネイティブに再設計できるかを一つの統合仕様として検証する。

1. 現状認識

\n

1.1 現行Showcaseが持つべき業務領域

\n

現行Showcaseは単純なCRMではなく、少なくとも以下を横断する業務基盤として考える。

  • 企業
  • 店舗
  • 企業担当者
  • スタッフ
  • スタッフ経験・スキル・希望条件
  • リード
  • 営業活動
  • 案件 / 求人
  • 企業側の求める条件
  • スタッフ側の条件
  • 応募
  • 候補者提案
  • 職場見学
  • 選考
  • 決定 / 不成立
  • 契約進捗
  • 稼働
  • 継続 / 更新 / 終了
  • 問い合わせ
  • 面談
  • タスク
  • コミュニケーション履歴
  • タグ
  • 結果理由
  • 社内ルール / 業務知識

将来的には花JOB、ハナワク、Zendesk、LINE、メール、電話等との連携も同じ業務コンテキストとして扱う。

2. コパンの現在の主要課題

\n

Showcase v2は技術デモではなく、以下の課題を解決するために作る。

2.1 営業活動の可視化が「報告依存」

\n

現在は営業担当者が活動後に入力する営業報告の品質・タイミングに依存する。

問題:

  • 入力が遅れる
  • 「営業活動」と「案件進捗・調整」が混在する
  • 次回アクションが不明確になる
  • 企業の反応が構造化されない
  • 後から集計はできてもリアルタイムな意思決定には弱い
  • 営業担当者の裁量で活動量を落としても発見しづらい
  • 新規営業と既存対応の時間配分が見えにくい

v2では「営業報告」という独立作業を可能な限り消し、業務イベントから自動生成する。

2.2 新規・既存・追客の優先順位が人間依存

\n

人間が企業一覧や履歴を読んで、

  • 今日どこに連絡するか
  • 何を話すか
  • いつ追客するか
  • 見切るか
  • 休眠させるか
  • 再活性化するか

を考えている。

v2ではAIが全リードを常時監視し、人間には「今日人間が触る価値が高い対象」を提示する。

2.3 案件進行の監視が人間依存

\n

案件の停滞理由が、

  • 候補者不足
  • 条件過多
  • 企業回答待ち
  • スタッフ回答待ち
  • 契約待ち
  • 面談待ち
  • 社内処理待ち

のどれなのかを人間が見に行く必要がある。

v2では案件をイベントとして監視し、停滞・異常・次アクションを自動判定する。

2.4 マッチング情報がまだAI学習に十分な形になっていない

\n

重要なのは「決まらなかった理由」だけではない。

  • なぜ企業がそのスタッフを選んだか
  • なぜスタッフがその企業を選んだか
  • どの条件が決定打だったか
  • 就業後に継続したか
  • 早期終了したか
  • 類似案件では何が効いたか

まで履歴化する。

2.5 スタッフ登録フォームが重くなりやすい

\n

業務効率化のために登録時入力を増やすと、スタッフ体験が悪化する。

v2では、

  • フォーム = 定量情報 / 事前取得
  • 人間面談 = 価値観、希望、ニュアンス、本質理解
  • AI = 面談前準備、記録、要約、構造化、タグ候補、未確認事項抽出

に役割分担する。

2.6 業務ルール・知識が人の頭にある

\n

「良い提案」「良い面談」「条件緩和交渉」「見切り基準」などが暗黙知になりやすい。

v2では知識を3種類に分離する。

  1. Hard Policy: 法令、絶対条件、承認権限、禁止事項
  2. Business Knowledge: 業務手順、判断基準、ノウハウ
  3. Case Memory: 実際に成功・失敗した案件や会話

3. Showcase v2 の設計思想

\n

3.1 Event First

\n

「現在の状態」だけでなく、「何が起きたか」を残す。

例:

  • lead.created
  • sales.call.completed
  • sales.visit.completed
  • requisition.created
  • requisition.condition_changed
  • staff.interview.completed
  • candidate.proposed
  • client.responded
  • match.accepted
  • match.rejected
  • placement.started
  • placement.renewed
  • placement.ended
  • ai.recommendation.created
  • human.correction.applied

イベントがAIの経験データになる。

3.2 Rule Before AI

\n

法令や絶対条件をLLMの推論に任せない。

例:

  • 派遣できない条件
  • 必須契約
  • 承認権限
  • 料金下限
  • 個人情報アクセス権
  • 外部送信禁止条件

これらはコード / Policy Engineで判定する。

AIは「曖昧な判断」「優先順位」「文章」「仮説」「提案」「要約」を担当する。

3.3 API / Tool First

\n

AIにDBを直接書き換えさせない。

AIは許可されたTool/APIのみを使う。

例:

  • get_company_context()
  • get_staff_context()
  • get_requisition_context()
  • search_candidates()
  • create_internal_task()
  • propose_next_action()
  • draft_company_message()
  • draft_staff_message()
  • update_requisition_status()
  • add_structured_tag()
  • request_human_approval()

すべて、

  • input schema
  • output schema
  • permission
  • validation
  • idempotency
  • audit
  • rollback方針

を持つ。

3.4 Human Authority

\n

AIが「人間を置き換える」のではなく、人間の判断価値が高い部分に集中させる。

人間が残すもの:

  • 企業との関係構築
  • スタッフ面談
  • 交渉
  • 例外判断
  • 感情を伴う対応
  • 重要な採否判断
  • 重大トラブル
  • 経営判断

AIに寄せるもの:

  • 記録
  • 要約
  • 検索
  • 監視
  • 集計
  • 転記
  • 下書き
  • タグ候補
  • 候補抽出
  • 次アクション候補
  • 異常検知
  • 原因仮説
  • 効果測定

3.5 Eval Driven Development

\n

AIの出来を「感覚」で評価しない。

機能ごとに、

  • 何を成功とするか
  • 何が失敗か
  • どの程度の精度が必要か
  • 人間が何を修正したか
  • 前バージョンより改善したか

を測れる状態にする。

3.6 Progressive Autonomy

\n

自律度は機能ごとに明示的に管理し、安全性とEval結果に応じて設定する。

  • L0: Observation — 見るだけ
  • L1: Suggestion — 提案のみ
  • L2: Draft — 下書き作成
  • L3: Approval Execute — 人間承認後に実行
  • L4: Autonomous — 条件付き自動実行

機能単位でレベルを持たせる。

5. Agent設計

\n

5.1 Agentを必要以上に分割しない

\n

v2の基本構成では、

Main Orchestrator + Skills + Tools

を基本とする。

理由:

  • Agent間通信はデバッグ難易度が上がる
  • Contextの重複が増える
  • コストが増える
  • 誤判断の原因特定が難しい
  • 役割境界を早期に固定すると将来のモデル性能向上を阻害する可能性がある

独立Agent化は、Evalで「分離した方が明確に精度・速度・保守性が上がる」と確認できた領域だけ行う。

5.2 Core Skills

\n

Sales Intelligence Skill

\n

役割:

  • 営業活動分類
  • 顧客反応抽出
  • 次回アクション抽出
  • 次アクション期限推定
  • 営業優先順位
  • 休眠リード再活性化
  • 既存クライアント増員兆候
  • 新規 / 既存 / オペレーション分類

Requisition Intake Skill

\n

役割:

  • 自然言語の依頼を構造化
  • 求人タグへ変換
  • 必須項目チェック
  • 未確認項目抽出
  • 条件矛盾検知
  • 条件緩和候補提示

Interview Copilot Skill

\n

役割:

  • 面談前ブリーフ
  • 聞くべき項目
  • 面談中の記録
  • 面談後の要約
  • スキル / 経験 / 希望タグ候補
  • 未確認事項
  • スタッフへの理解メモ
  • 次に紹介しやすい案件タイプ

Matching Skill

\n

2段階にする。

Stage 1: Deterministic Filter

\n
  • 勤務地
  • 勤務開始
  • 曜日
  • 時間
  • 法的条件
  • 必須資格
  • 必須経験
  • 絶対NG条件

Stage 2: AI Ranking

\n
  • 経験適合
  • 仕事内容適合
  • 希望適合
  • 類似案件実績
  • 継続可能性
  • 企業傾向
  • スタッフ傾向
  • 過去の成功 / 失敗パターン

結果:

  • match_score
  • 推薦理由
  • 懸念事項
  • 確認事項
  • 過去類似事例

Case Manager Skill

\n

案件を常時監視。

検知:

  • 24/48/72時間動きなし
  • 候補者ゼロ
  • 企業回答待ち
  • スタッフ回答待ち
  • 面談未設定
  • 契約停滞
  • 開始日接近
  • 更新期限接近
  • 異常なステータス遷移

通知だけでなく、

  • 原因仮説
  • 推奨アクション
  • 誰が対応すべきか
  • 期限

まで出す。

Retention / Expansion Skill

\n

稼働後の監視。

  • 初日
  • 3日
  • 14日
  • 1ヶ月
  • 更新前

企業 / スタッフの双方から、

  • 離職兆候
  • 不満
  • 条件不一致
  • 更新可能性
  • 増員需要
  • 他部署需要

を検知する。

Process Improvement Skill

\n

全業務Traceを分析。

例:

  • 最近、候補者提案までの時間が悪化
  • 特定項目の人間修正率が高い
  • 同じ確認作業が繰り返されている
  • ある営業担当だけ次回アクション未設定が多い
  • 特定条件の案件だけ充足率が低い
  • 新規営業が不足
  • 職場見学など非営業作業が営業KPIに混入

結果として、

  • 業務ルール変更案
  • UI変更案
  • 入力項目変更案
  • 自動化候補
  • AI Prompt変更候補
  • 新規Eval候補

を作る。

7. 「結果理由」を資産化する

\n

案件結果では以下を別々に持つ。

7.1 決まらなかった理由

\n

例:

  • スキル不足
  • 経験不一致
  • 曜日
  • 時間
  • 距離
  • 給与
  • 企業選考
  • スタッフ辞退
  • 他候補決定
  • タイミング
  • 連絡不能
  • 条件変更
  • 案件消滅

7.2 決まった理由

\n

例:

  • 必須経験一致
  • 類似業務経験
  • 勤務条件一致
  • 長期就業可能
  • 即勤務可能
  • 人物相性
  • 技術力
  • コミュニケーション
  • 勤務安定性
  • 柔軟性
  • 過去実績
  • 企業要望に対する特殊適合

タグだけでなく、可能なら

  • human_selected_reason
  • ai_inferred_reason
  • client_stated_reason

を分ける。

「AI推定」と「人間/顧客が明言した事実」を混ぜない。

8. Context Engine

\n

AIに毎回DB全件を渡さない。

そのタスクに必要な高シグナル情報だけを構成する。

8.1 Context優先順位

\n
  1. Hard Policy
  2. 現在の案件 / 対象レコード
  3. 直近イベント
  4. 関連する企業 / スタッフ
  5. 関連する過去事例

16. Durable Execution

\n

AI業務は途中で、

  • API Timeout
  • モデル障害
  • ネットワーク切断
  • 外部サービス障害
  • 人間承認待ち
  • 数時間 / 数日待機

が発生する。

そのため、

AI Agentの処理を通常のHTTP Request単発処理だけで作らない。

必要要件:

  • Checkpoint
  • Retry
  • Resume
  • Timeout
  • Scheduled Resume
  • Human Interrupt
  • Idempotency
  • Dead Letter / Error Queue
  • Cancel
  • Compensating Action

候補技術:

  • Temporal
  • LangGraph persistence
  • Dapr / Restate
  • その他同等のDurable Workflow基盤

エンジニアが比較しADRを作成する。

18. AI Model Strategy

\n

特定モデルにシステム全体を固定しない。

  • 速度
  • コスト
  • Context
  • Tool Use
  • Voice
  • Structured Output

をEvalし、最適モデルを使う。

例:

  • 軽い分類 → 高速・低コストモデル
  • マッチング説明 → 中〜上位推論モデル
  • 難しい業務改善分析 → 高推論モデル
  • Voice → Realtime Voice Model

OpenAI / Anthropic / Google等を差し替え可能な設計にする。

ただし「マルチモデル対応」のために抽象化を過剰にしない。

最低限、

  • model_provider
  • model_name
  • prompt_version
  • parameters
  • trace_id

を保存する。

20. Historical Replay / Digital Twin

\n

v2の非常に重要な実験機能。

過去の業務データを使って、

「その時点でAIが存在していたら何を提案したか」

を再生する。

例:

2026-04-01時点の案件情報だけをAIに与える。

AI:

  • 誰を候補にするか
  • 何を次アクションにするか
  • 条件緩和を提案するか

実際の結果と比較。

これにより、本番で顧客に影響を与えずAIを検証できる。

重要:

未来情報リークを防ぐ。

Replay時点以降に発生したデータをContextへ入れない。

21. Shadow Mode

\n

Showcase v2は本番データをMirrorしてShadow Modeを実行できる構造とし、

AIは判断するが実行しない。

人間の実際の行動と比較する。

例:

AI推奨:
A社へ本日追客

実際:
営業担当者はB社へ電話

3日後:
A社から案件発生

こうしたデータを比較する。

Shadow Modeで評価できるもの:

  • Next Best Action
  • Candidate Ranking
  • Stale Case Detection
  • Churn Risk
  • Expansion Opportunity
  • Sales Classification

22. Feature Flag / Canary

\n

AI機能を一括リリースしない。

例:

  • 全社員OFF
  • 管理者だけON
  • 1担当者のみON
  • 10%案件
  • 特定企業除外
  • Draft Only
  • Approval Required
  • Autonomous

まで制御。

問題があれば即OFF。

23. Observability

\n

AIの「ログ」だけでは足りない。

最低限、

  • trace_id

  • event_id
  • user_id
  • entity_id
  • prompt_version
  • model
  • input tokens
  • output tokens
  • latency
  • cost
  • tool calls
  • tool result
  • approval
  • final outcome
  • correction
  • error

を追えるようにする。

OpenTelemetry互換を推奨。

個人情報をTraceに無制限保存しない。

24. Security / Containment

\n

自律AIは「賢さ」よりBlast Radius管理が重要。

必須:

  • Least Privilege
  • ReadとWrite Toolを分離
  • 本番DB直接接続禁止
  • SecretをPromptに入れない
  • External Contentを信用しない
  • Prompt Injection対策
  • 外部送信は原則Human Approvalを標準とし、Evalと権限設計で安全性が確認されたActionのみ自動化可能
  • 削除 / 契約 / 料金変更は強制承認
  • 全Tool Audit
  • Idempotency Key
  • Rate Limit
  • Cost Limit
  • Agent単位Budget
  • Emergency Kill Switch
  • PII Masking
  • Data Retention Policy

AI SandboxとCredential管理を分離する。

36. 2026年時点の技術的根拠

\n

今回の方向性は概念だけではなく、現在の主要AI開発基盤で実装可能なものになっている。

Agent Tool Use / Trace / Sandbox

\n

OpenAI Agents SDKでは、Tool、Handoff、Guardrail、Tracingに加え、2026年にはSandboxを使った長時間Agent実行が強化されている。

Self Improving

\n

OpenAI / ThriveのTax Agent事例では、

Human Correction → Product Trace → Eval → 改善

というループが実装されている。

Showcaseでも同じ考え方を業務判断へ転用する。

Eval

\n

AnthropicはAgent Evalについて、

  • task
  • trial
  • grader
  • transcript / trace
  • outcome
  • eval harness

を分け、Capability EvalとRegression Evalを組み合わせる設計を推奨している。

Long Running Development

\n

Anthropicは長時間Application開発で、

Planner / Generator / Evaluator

と、Sessionを跨ぐStructured ArtifactによるContext引継ぎを実証している。

Context Engineering

\n

現在はPrompt Engineeringだけではなく、

  • Instructions
  • Tools
  • Context
  • Memory
  • Retrieval
  • History

全体を最適化するContext Engineeringが重要。

MCP

\n

MCPはAgentとTool / Dataを接続する標準として進化し、2026-07-28仕様ではstateless core、Multi Round-Trip Requests、authorization hardening、tasks等が追加されている。

A2A

\n

A2AはAgent間連携のオープン標準としてLinux Foundation配下で進み、2026年には主要クラウドを含む多数の組織が参加している。

Durable AI

\n

Temporal等のDurable Executionは、長時間Agent、Human Approval、Retry、障害復旧を通常の業務システムとして扱うために有効。

Voice

\n

Realtime Voice Modelは、

  • listen
  • reason
  • transcribe
  • tool use
  • action

までリアルタイムに実行できる段階に来ている。

37. AI BUILDERへの指示

\n

以下をこの資料と一緒にAIへ渡す。

あなたはShowcase v2のLead Architect / AI Engineerです。

この資料を「完成仕様」とみなして盲目的に実装してはいけません。

まず現行Showcaseの実コード、DB、API、画面、運用を調査してください。

本資料と現行実装に矛盾がある場合は、現行実装を事実としてGapを明示してください。

既存Showcaseを壊さず、v2 Sandbox上でEnd-to-Endに動く構成を設計してください。

技術選定には必ずADRを作成してください。

AIが判断する項目、コードで決定する項目、人間承認が必要な項目を分けてください。

AIのすべての判断・Tool Call・結果はTrace可能にしてください。

Human Correctionを捨てず、Eval Dataset化できる構造にしてください。

機能実装前にAcceptance Test / Evalを定義してください。

一度に巨大な変更をせず、小さなTaskへ分解してください。

各Task終了時に、テスト、ドキュメント更新、未解決事項を残してください。

複雑なMulti-Agent構成は、Single Orchestrator + Skillsより優れていることがEvalで確認されるまで採用しないでください。

Productionへの外部Writeは、明示的に許可されるまで禁止です。

仕様にないコードやデータ構造を想像で作らず、必ずCurrent Codeから確認してください。

コード実装と並行して必ず以下の設計成果物を作成・維持し、 Current Architecture / Gap Analysis / Target Architecture / Event Catalog / Tool Catalog / Policy Matrix / Eval Plan / ADR候補 としてください。

38. 最終到達イメージ

\n

Showcase v2が目指すのは、

人がシステムを見る
↓
問題を探す
↓
考える
↓
入力する
↓
誰かに依頼する

ではない。

業務Event発生
↓
Showcaseが観測
↓
Rule適用
↓
AIがContextを理解
↓
必要Actionを判断
↓
自動実行 or Human Approval
↓
結果を観測
↓
人間修正を保存
↓
Eval
↓
業務 / AI / UIを改善

である。

最終的には、

コパンの仕事をShowcaseに記録するのではなく、Showcaseの上でコパンの仕事そのものが動く。

そして、

仕事が動くほど、成功・失敗・人間修正が蓄積され、次の判断と業務設計が改善される。

ここをShowcase v2の北極星とする。

01

目的・最終ゴール

Executive summary

省力化だけではなく、AIが実務を引き受け、同じ組織でより多くの派遣稼働を管理できる体制をつくる。

GOAL 01

人間の総作業時間を80%削減

生成・送信・更新・分析・追加作業をAIへ移し、例外・承認・対人対応に集中する。

GOAL 02

稼働人数を現在の3倍へ

現在約15名から45名を目標に、営業・採用・打診・継続を連動させる。

GOAL 03

AI停止中でも業務継続

システムだけでなく、手順、責任者、作業確認、訓練まで人間の代替運用を準備。

最も重要な前提： 80%削減と3倍稼働は目標値であり、現時点の達成見込みや確約ではない。現行の業務別所要時間、稼働開始人数、対応品質を基準値として測定する。

03

Dotsを中心に置いた全体アーキテクチャ

前提を明確化する。AI判断エンジンをコパン側に別途構築する構想ではない。 Dots自身が業務を考えて実行する。コパン側は、必要な情報と安全な操作手段を提供する。

Dots ｜ AI実務担当者仕事の取得 → 情報参照 → 判断 → 文章生成 → 操作 → 結果確認 → 改善
↕
AI専用ワークスペース作業キュー・要約情報・実行操作・結果・引継ぎ
接続アダプター（必要時）標準API / 将来MCP等へ差し替え可能
↕
コパン標準API ＋ 安全な実行処理参照・送信要求・ステータス変更・履歴保存・権限・重複防止
↕
既存の業務DB企業 / 受注 / スタッフ / 打診候補
外部サービス・成果DBLINE / 求人 / SNS / 広告 / 実行履歴
↕
人間用管理画面 ｜ 代替作業・承認AIと共通の仕事台帳、マニュアル、チェック項目、作業引継ぎ
「AIが仕事をする」の意味： Dotsが「誰に・何を・いつ・なぜ実行するか」を判断し、ワークスペースから実行を依頼する。LINEへの通信、DBの確定更新、重複防止などの機械的な処理はAPI側が実施する。操作主体と責任の境界を分ける。

仕事の起動から完了まで

01 発生受注・回答・期限・異常
02 仕事登録DBに作業IDと状態
03 Dots作業取得・判断・指示
04 API処理送信・更新・検証
05 結果・再作業成果を保存し次を判断

仕事発生をDotsに届ける方法は未確定。定期的な専用画面確認などで実証する。Dotsへ外部システムから任意の時点で確実に即時起動できる、とは現時点では前提にしない。

LINE名寄せとスタッフ打診の自動化

既存環境

現時点で存在するもの

LINE公式アカウントを使用し、スタッフへの打診はLINEが中心。コパンシステムには「打診候補化」機能がすでに実装されている。

未実装

追加が必要なもの

スタッフIDとLINEユーザーIDの紐付け。スタッフログイン機能は現状ない。送信・回答・履歴の自動連携は開発対象。

A. 名寄せ：LINE公式アカウント + SMS

1
LINEから「会員情報を連携」を開始

既存公式アカウントのトーク／メニューから開始。Webhookで対象のLINEユーザーIDを取得。

2
登録済み携帯電話番号を照合

スタッフマスタの番号にSMSワンタイムコードを送信。任意の別番号で本人確認を成立させない。

3
LINE公式のアカウント連携を完了

連携トークン、使い捨てnonce、LINEの連携成功Webhookを検証してスタッフIDと確定紐付け。

4
重複・変更・解除を管理

同じ電話番号の複数登録、電話番号変更、既存連携との競合は有人確認へ。解除後は送信停止。

氏名・生年月日・LINE表示名だけでは自動名寄せしない。SMSは登録番号を現在利用できることの確認であり、厳密な身元確認と同一ではない。

SYSTEM FIRST

08

AI停止時の「人間代替」を必須機能にする

AI停止時に必要なのは復旧機能だけではない。社員が仕事を引き継ぎ、業務を続けられるシステム・組織・作業手順を最初から準備する。

MODE A

AI通常運用

Dotsが担当。必要な承認だけ人間が実施。

MODE B

人間代替運用

同一の仕事台帳から、人間が作業とチェックを引き継ぐ。

MODE C

縮退・緊急運用

重要業務を優先。AI以外のシステム／LINE停止にも備える。

停止・復旧時の標準フロー

01
異常検知・通知

処理停滞、応答停止、実行エラーを検知し、一次担当と代理担当へ通知。

02
新規自動実行の停止・ロック

AIによる新規実行を保留。未処理・実行中・送信結果不明を区別する。

03
人間への担当割当・引継ぎ

案件、作業目的、対象、前回操作、未確認事項、次にすべきことを提示。

04
手順書・チェックに沿った代替実行

対象確認 → 重複確認 → 操作 → 結果確認 → 履歴登録。確認者を指定する。

05
復旧後の突合・管理者承認

AI停止中に人間が処理した内容、実行中の結果、残タスクを照合してからAI再開。

権限・安全性・品質保証

操作の種類原則の実行方式備考
情報取得・集計権限内で自動業務に必要な最小項目だけ取得
承認済み文章のLINE送信段階的に自動化送信対象・頻度・配信停止・重複・上限を検査
新しい配信文の初回実行初期は人間承認修正履歴・成果を見て承認範囲を拡大
契約、給与、個人情報変更人間の最終確認法令・本人確認・監査証跡を重視
広告予算・広範囲の外部公開予算上限＋必要な承認媒体仕様・費用リスクを管理
障害復旧・AI再開管理者承認処理中タスクと二重実行を照合
APIが守る安全装置：認証、最小権限、利用期限、レート制限、送信上限、二重実行防止、操作ログ、失敗時の停止。これらはDotsがどのように判断しても迂回できないようにする。

LINEではWebhook署名の検証を行い、Push APIのリトライキーを利用して再送に伴う重複を抑える。失敗・タイムアウトでも既に受理済みの可能性があるため、無条件の再送は禁止。

個人情報の原本とAI改善用の分析情報は原則分離し、改善データには匿名化・仮名化を活用。利用目的、保存期間、アクセス権限、外部AIへの提供範囲を定める。

未検証・未決定事項

企画としての採用と、技術・運用としての成立は分けて判断する。

01｜Dotsが長時間・繰り返し作業できる運用条件
クラウドブラウザー経由のログイン、作業取得、進捗保存、継続実行、制約・利用枠、停止や承認待ちの発生条件を実環境で確認する。利用可能プランと組織管理設定も要確認。
02｜外部イベントでの作業開始方法
コパン側の受注イベントをDotsへ直結できるかは確定していない。初期は定期確認など現実的な起動方式で実証。即時性が必要なWebhook保存や作業登録はシステムが処理する。
03｜AI専用UIが本当に効率的か
画面認識型・構造認識型など内部操作方式を固定的に想定しない。操作回数、1件処理時間、エラー、再実行、確認できる利用量を測定し、投資対効果で判断する。
04｜LINE名寄せ・Webhookの既存設定
現行プロバイダー、チャネル、Webhook URL、有人チャット・既存連携への影響、携帯番号の重複・未登録、SMS送信サービスを確認。既存設定は調査前に変更しない。
05｜広告・求人媒体への公開権限
媒体ごとのAPI仕様・審査・送信権限・広告予算操作上限を確認。投稿の可否を一律に約束しない。
06｜人間代替体制と業務の優先順位
一次担当・代理担当・最終承認者、縮退時に止めてはいけない仕事、手動運用の最大処理能力、訓練頻度を確定する。
07｜現状KPI・コストの基準値
業務別人時、打診回答率、稼働までの日数、求人獲得費、サービス利用枠、インフラ・SMS・API費用を実測して計画を確定する。

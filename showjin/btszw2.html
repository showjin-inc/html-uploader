showrap — 本番展開に向けた技術方針

相談用ブリーフ §6「相談・判断してほしいこと」への回答。スタック／インフラ／DB／認証／テスト運用／工数の現時点の結論を整理する。

対象：笑人 予実・資金繰りシステム「showrap」（Excel卒業）／ 現状：動くプロトタイプ（Vanilla JS ＋ localStorage）→ 社内テスト展開

0結論サマリー

プロトタイプの資産を活かし、フロントは Vanilla JS を維持したまま、データ層（localStorage）だけを API＋DB へ載せ替える方針。技術的な難所はフロントではなく、履歴・権限・provenance を持つバックエンドとデータモデルにある。インフラは AWS 上で Fargate ＋ RDS ＋ S3、認証は既存 Cognito を流用する。

全体像 フロント維持（Vanilla JS） ／ バックエンド Node.js(TypeScript) ／ DB は MySQL(RDS) ／ インフラは Fargate＋RDS＋S3 ／ 認証は既存 Cognito ／ DEV・本番は完全分離。

1フロントエンド：Vanilla JS を維持

Vanilla JS を維持し、React 化は行わない（開発規模が大きく育った段階で将来検討）。既存の app.js（約5,000行）には「動く仕様」＝暗黙の要件定義と、検証済みの入力UI（特に現場ワークシート）が詰まっている。全面書き換えは、この資産と検証結果を捨てることになり、費用対効果・リスクの両面で見合わない。

移行は「フロントは再利用、データアクセス層だけを localStorage → API 呼び出しに差し替える」形で進める。

2バックエンド言語：Node.js（TypeScript）

AI 主体の開発のため言語自由度は高いが、Node.js（TypeScript）を推奨。理由は、既存 app.js の計算ロジック（単価×数量、率×他行、原価率判定、集計・連結など）が同一言語なので移植の翻訳コストが最小で、フロントと言語統一により人・ツールを共有できるため。金額を扱うため TypeScript で型を効かせ、事故を減らす。

3データベース：MySQL（RDS）

主データストアはリレーショナルDBが正解（S3 に JSON を置く案は主データには不適 —— ロック・トランザクション・結合クエリがなく、複数人が同月を触ると破綻する）。

エンジンは技術的には Postgres・MySQL どちらでも成立する（再帰CTE・JSON型・ウィンドウ関数はどちらも対応）。決定打がないため、社の標準に合わせて MySQL 8 を採用。ShowCase・Copain・花ワクが MySQL であり、バックアップ・監視・運用ノウハウを共有でき属人化を避けられる運用メリットが上回る。データ量は小さく、最小インスタンス（db.t4g.micro〜small）で十分。

補足：個人の好みは Postgres だが「困らないなら周りに合わせる」を優先。将来 showrap 専任運用・Postgres固有機能の積極活用が必要になれば再考する。

4インフラ：Fargate ＋ RDS ＋ S3

コンピュートは ECS Fargate（OS・パッチ管理不要で少人数運用向き）。DB は RDS（MySQL）。基本は「Fargate＋RDS」で成立するが、S3 も設計に含める。

  • MoneyForward CSV 取込の一時置き場（アップロード → パース → 取込）
  • DBバックアップ／エクスポート（Excel・PDF）の出力先
  • （任意）フロントの静的配信。Fargate コンテナから直接配信してもよい

DEV と本番は別スタックで完全分離（可能なら別アカウント、最低でも別DB＋環境変数）。認証・認可は §5、コストは §7 を参照。

[利用者] └─▶ ALB ─▶ ECS Fargate（API: Node.js / TypeScript ＋ Vanilla JS 配信） ├─ RDS (MySQL) … 本体データ（計画・実績・資金繰り・履歴） ├─ S3 … MF CSV取込 / エクスポート / バックアップ ├─ Cognito（既存プール流用） … 認証 └─ Secrets Manager / CloudWatch Logs ※ DEV 環境と 本番環境 は別スタック（可能なら別アカウント）で完全分離

5認証：既存 Cognito を流用

認証方式はメール＋パスワードで確定。既存（ShowCase / Copain）の Cognito を流用する方針で妥当。実装上の要点：

  • 既存 User Pool を再利用し、showrap 専用の App Client を新規発行する（対象ユーザーが既存プールに揃っていれば SSO になり体験も良い）。
  • 認証＝Cognito、認可＝アプリ側に寄せる。役割（全権管理者／経理／管理／閲覧）とスコープ（表示可能な会社・拠点）は仕様が細かいため、アプリ側DBで管理するのが素直。
  • テスト環境は別 User Pool（または別 App Client）を用意し、本番アカウントを社員のテスト操作で汚さない。

6テスト環境の運用：リセット＆シード

「社員が壊してもOK」は、画面上の機能として3段階で用意する。DEV 専用の別 RDS（本番と完全分離）とあわせて、ボタン一発で初期状態へ戻せる状態にする。

  • ① データリセットボタン（最優先）　管理者・DEV限定。マスタ系（ユーザー・会社・組織・勘定科目・権限）は残し、トランザクション系（計画・実績・資金繰り明細・ワークシート・変更履歴）を初期シードへ戻す。リセット範囲＝何を残すかは要相談。
  • ② シーダー（テストデータ投入）　想定データをスクリプト化し、ボタンで投入。デモに近い初期状態を毎回再現できる。
  • ③ スナップショット保存＆復帰（後追い可）　データ量が小さいため、時点の全データを名前付きで保存 → 後で復元、が現実的に作れる。優先度は①②より下。

7コスト概算（東京リージョン）

知識ベースの概算。確定は AWS Pricing Calculator で。単位は USD/月、円換算は 1ドル≒150〜160円。

構成内容本番/月
リーン案EC2 t4g.small 1台 ＋ RDS t4g.micro ＋ S3（ALB/NATなし）約 $40〜55
標準案（推奨）Fargate小 ＋ ALB ＋ RDS t4g.micro(Single-AZ) ＋ S3約 $70〜90
本番堅牢案上記 ＋ RDS Multi-AZ ＋ NAT Gateway約 $140〜170
コストの罠：①ALB（トラフィック0でも基本料 ≈ $18/月）②NAT Gateway（≈ $45/月＋通信）。Fargate をパブリックサブネット＋SG で運用するか VPCエンドポイントで NAT を回避すれば節約できる。DEV 環境は夜間・休日に RDS 停止＋スケール0で 月$20〜40 程度に抑えられる。

8工数・期間の概算

スキーマ・API設計・リセット範囲などが未確定のため粗い当たり。1名（経験者・AI補助あり）想定の人日レンジ。

フェーズ内容人日
0 設計DBスキーマ・API設計・環境設計5〜10
1 インフラ/IaCFargate＋RDS＋Cognito、DEV/本番、CI/CD5〜10

暦の目安は 1名で約3〜5ヶ月、2名で約2〜3ヶ月。AI主体で定型部分を圧縮すれば2〜3割短縮も見込めるが、金額・権限まわりのレビューと検証は削らない。最も重いのはフェーズ2（全体の3〜4割）で、provenance・速報履歴・ロック・変更履歴といった「履歴と状態」の設計が要因。

9実装前に握るべき論点

  • MoneyForward 連携：会計は CSV/API 取込。給与だけは MF給与API が非公開のため CSV/手入力。
  • provenance（出所）：確定＝会計／速報＝各ソース／手入力、をスキーマにどう落とすか。
  • 金額単位：内部は千円、資金繰りの実残高だけ円。
  • リセット範囲：残すマスタ／消すトランザクションの線引きの最終確定。

10次のステップ

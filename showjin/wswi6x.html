1. 目的

顧客向けの統合ポータル「emie」を新設し、次を実現する。

  • 顧客は emie に1回ログインすれば、所属企業の Copain・花Job・ハナワクへ再ログインなしで移動できる（SSO）。
  • emie のダッシュボードから、所属企業・店舗の各サービスの情報を横断的に参照できる。
  • 会社名・店舗などの基本情報を1か所に集約し、どのサービスから見ても一貫させる。

emie のユーザーは ShowCase / Copain のユーザーと共通。ShowCase は運営者用の管理画面、emie は顧客用の入口で、両者は同じ基盤の表裏の関係にある。

2. 現状（As-Is）

ShowCase（運営）と Copain（顧客）は単一の MySQL（RDS 1 インスタンス／DB 名 copain）を共有し、Eloquent モデルは共有ライブラリ shared-core に集約されている。企業・店舗・ユーザー・権限はすべてこの共通DBにあり、アプリ間のAPI連携は無く、両アプリともDB直接アクセス。テナント（企業）の切替はサーバサイドのセッション selected_company_id で行う。花Job・ハナワクは apps テーブルに行としては存在するが、実装・専用テーブルはこのリポジトリには無い。

システムドメインインフラ / DBログイン単位
ShowCase（運営）show-case.appECS ／ 共通RDS（DB名 copain）運営者（operator_level で区別）
Copain（顧客）copain.jpECS ／ 共通RDS（同上）ユーザー単位・所属企業を切替

設計に効く現状の事実

  • users.email に DB の UNIQUE 制約が無い。重複防止はアプリ層のバリデーションのみで、論理削除済みの同一メール行が複数あり得る。
  • cognito_sub は実 sub ではない（すべてアプリ生成のダミーUUID）。Cognito ログインとローカル行の突合は現状 email 一本。
  • ID トークンの検証は未実装。AdminInitiateAuth で成否だけ受け取り、以降は Laravel の DB セッションで認可。ALB の Cognito 認証は無効化済み。ロールは Cognito ではなく DB（operator_level / permission_level）にある。
  • テナント分離は各コントローラの手書き（where('company_id', session(...))）。グローバルスコープは無い。
  • 企業・ユーザーを提供するAPIは皆無。ShowCase / Copain は同一RDS・同一DBを共有（sessions/cache/jobs も同一）。
  • 店舗（stores）は共通DBに存在（companies 1:N）。ただし業態フラグ・繁忙期フラグ・store_dispatch_configs（70項目超）は派遣・花系固有。
  • 企業・店舗・ユーザーのIDはすべて連番。外部システムIDを持つカラムは1つも無い（名寄せ用の対応表が別途必要）。

3. 全体構成（To-Be・確定版）

企業・店舗マスターは共通DB（RDS）だけが持つ「正本（SSoT）」とする（＝案②）。内部の3アプリ（ShowCase・Copain・emie）は同じモノリポ・同じRDSなので共通DBを直接参照する。外部の花Job・ハナワク（EC2）は emie が提供するAPI経由でつなぐ。emie は業務データを各サービスのAPIから取り寄せて集約表示する。

4. データの持ち方とモデル

情報は3種類に分けて扱う。

  • ユーザー情報（ログインアカウント・所属）… 共通DB＋Cognito に集約（1か所）。花Job・ハナワクには持たせない。
  • 企業・店舗マスター（会社名・店舗名・住所など共通の基本情報）… 共通DB(RDS)だけが正本。各サービスは参照・更新する（写しは持たない）。
  • 業務データ（花Job＝求人、ハナワク＝シフト等）… 各サービスのDBに保持。emie は必要時にAPIで取得。

主なテーブルと名寄せ

共通DBは users（アカウント）、user_company_permissions（ユーザー↔企業の多対多＝テナント境界）、companies（企業マスター）、stores（店舗マスター・企業1:N）、権限系（user_company_permissions / user_app_permissions / apps / company_app）で構成される。emie でもこの構造を正本として使う。

各システムのIDは連番で、外部システムIDを持つカラムが無いため、中央ID ↔ 各サービスの企業/店舗アカウントID を対応づける変換表（クロスリファレンス）を新設する。名寄せの実用キーは apps.app_code（機能中）、corporate_number（法人番号・補助扱い）、email（要 UNIQUE 化）。

5. 認証とSSO

5.1 認証

認証は Cognito を元締めとするが、現状どおり各アプリが自前のログイン画面＋AdminInitiateAuth＋Laravel セッションで扱い、内部アプリでのトークン検証は実装しない（決定 ⑦-a）。ロールの正本は引き続き DB に置く（決定 ⑤）。ログイン時に本物の sub を書き戻し、既存のダミー値は NULL 化する（決定 ⑥）。

5.2 SSO は全行き先で「ハンドオフ方式」

ShowCase(show-case.app) / Copain(copain.jp) / emie(emie.ltd) は3つとも別の登録ドメインで、ブラウザのログイン状態（クッキー）はどの組み合わせでも共有できない。したがって「1回ログインで自動的に共有」は成立せず、どこへ行くにも受け渡し（ハンドオフ）が必要になる。emie を入口（ID ハブ）に、短命チケットを渡して各サービスへ遷移する（決定 ⑧）。

図2. SSO ハンドオフの流れ

検証は2パス。内部（Copain / ShowCase）は同一RDSなので着地側が共有 sso_tickets を直接消費（APIキー不要）。外部（花Job / ハナワク）は emie の検証API を APIキー付きで呼ぶ。着地側の前提として、CSRF 検証の除外（課題14）とクッキー SameSite=lax の維持が必要。

安全面の要点：なりすまし対策は「TTL 60秒／ワンタイム／POST限定／行き先束縛」の4点で担保する（PKCEなしのOAuth認可コードと同等）。APIキーは検証APIの直叩き（情報漏えい）対策であって、チケット奪取そのものは防がない。この理解が「内部パスでAPIキーを省く」判断の根拠。

6. 決定サマリ

#論点決定
①users.email の一意化素の UNIQUE(email) ＋ shared-core の UserObserver で退避／復元（復元時に衝突したら中止）。照合順序が大小・末尾空白を吸収するため正規化カラムは不要。
②マスターの書き込み権限全サービス（外部含む）から書き込み可。単独利用の顧客がいるため参照のみは機能後退。
③法人番号 corporate_number補助扱いのまま（必須化・UNIQUE化しない）。統合時に企業の手動マッピング工程を見込む。
④データアクセス経路内部（ShowCase/Copain/emie）はDB直参照、外部（花Job/ハナワク）のみ emie マスターAPI経由。境界はデプロイ先。
⑤ロールの正本DBのまま（Cognitoグループへ移さない）。認証＝Cognito／認可＝DB参照。
⑥cognito_sub の本物化ログイン時に IdToken の sub を書き戻し、既存のダミー値は NULL 化（遅延埋め）。
⑦-a内部3アプリの認証現状方式を継続（自前ログイン＋AdminInitiateAuth＋セッション）。トークン検証は実装しない（access_blocklists の防御を残すため）。
⑦-b外部からのAPI認証emie 画面で発行・失効する API キー＋ acting user の明示。認可は必ずDBを引く。
⑧シームレスSSO（全行き先）emie を ID ハブとしたハンドオフ方式。60秒・ワンタイムの opaque チケットを POST で渡す。検証は内部＝共有DB直消費／外部＝検証API＋APIキーの2パス。

※ 旧・課題11（ドメインを揃えてセッション共有する案）は retire。3つとも別ドメインで原理的に不可能なため。

7. 実装の順序と前提

着手前の前提（未整備・要対応）：
  • emie.ltd のインフラが全部新規（Route53・ACM証明書・ALB host ルール・APP_KEY）。CDK変更が必要（課題12）。
  • app/emie 本体が未作成（app/ は copain / shared-public / showcase のみ）（課題13）。
  • 着地エンドポイントの CSRF 除外設定が必要（課題14）。SameSite=lax の維持も前提。
  • 本番／dev RDS でのメール重複の再棚卸し（ローカルは0件だが本番で0件かの確認が①の前提）。

推奨する順序

  1. emie.ltd インフラ＋app/emie 本体の用意（前提）。
  2. 共通DBの地固め：email の UNIQUE 化＋UserObserver、実 sub の書き戻し。既存不具合（forceDelete() 削除、deleteUser() の IAM 権限、cognito_pool_kind 追随）も対応。
  3. マスターAPI と ⑦-b の API キー基盤。API仕様（入出力）を先に確定し、外部の実装と並行できるようにする。
  4. ⑧ のハンドオフSSO（sso_tickets テーブル、SsoTicketService、発行 POST /go/{app_code}、検証 POST /api/sso/tickets/verify）。実装順は ⑦-b → ⑧。
マスターAPI 初期設計の必須3点：①バルク取得エンドポイント、②変更通知（shared-core のモデル Observer で発火＝直書きも取りこぼさない）、③分析用の読み取り専用経路。API側に「自分が唯一の書き手」前提のキャッシュ等を作り込まないこと。

8. 外部連携（花Job・ハナワク）

花Job・ハナワクはユーザー概念がなく、企業単位／店舗単位のアカウントで運用されている（同一の担当先）。そのため対応づけは「企業／店舗アカウント ↔ 中央ID」で行い、ユーザーテーブルの新設は不要。実装は本リポジトリに無いため、次を担当先に確認する（課題10）。

  • アカウント単位（企業／店舗）と ID の形式 ／ 現在の認証方式。
  • 【重要】emie からの受け渡しを受けて、パスワードなしで「その企業／店舗としてログイン状態にする」着地口を新設できるか（＝SSO着地の可否）。
  • 企業・店舗情報の編集画面の有無と、共通DB参照・更新への変更可否。
  • emie に返せる業務データ（求人／シフト等）の項目・単位。

当方は「認証・emie入口・チケット発行・検証API＋APIキー・マスターAPI・API仕様」を用意し、担当先は「SSO着地口・マスターのAPI参照更新化・業務参照APIの提供」を対応する、という役割分担。
